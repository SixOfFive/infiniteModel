# Node: RTX 3060 (Ampere, sm_86)

Three RTX 3060s appear in the fleet. They share an arch (**Ampere, compute capability sm_86**)
but differ in VRAM, host OS, and role — one (`beast`) is even a host's *second* GPU, run as a
co-located extra worker beside its 4070 Ti SUPER.
Ampere is **sm_80+**, so the fused-MoE opt-in (`INFINITEMODEL_CUDA_FUSED_MOE`) is supported on
both in principle — see [../ACCELERATION.md](../ACCELERATION.md).

| Host | Card | VRAM | OS | Role | Persistence |
|---|---|---|---|---|---|
| **amdcomp** | RTX 3060 | 12 GB | Proxmox VE 9 / Debian 13 | GPU worker (full pipeline stages; also a `can_t2i` / t2a media target) | systemd system unit `im-worker.service` |
| **mobile** | RTX 3060 Laptop | 6 GB | Debian 13 (trixie) since 2026-08-10 | ⚠ **no NVIDIA driver installed** — see [§0](#0-mobile-status-after-the-debian-reinstall) before using anything below | ⚠ unknown post-reinstall |
| **beast** | RTX 3060 (GPU 1) | 12 GB | Proxmox VE 9 / Debian 13 | GPU worker on beast's **second** card (GPU 0 is the 4070 Ti SUPER). Run as a co-located second worker `beast-3060` — recipe + collision points in [4070-ti-super.md §3.1](4070-ti-super.md#31-second-worker-for-the-rtx-3060-gpu-1) | systemd system unit `im-worker-3060.service` |

> **`amdcomp` is the box formerly called `theocomp`** — same hardware (AMD CPU, hence the name;
> the GPU is NVIDIA, so this is CUDA, not ROCm), wiped and rebuilt as a Proxmox VE host. Older
> notes, unit backups, and `validate_vram_plan.py`'s fixture names still say `theocomp`; they
> mean this machine. The name is not used anywhere else in this doc.

## 0. `mobile` status after the Debian reinstall

**Open questions this repo cannot answer.** Nothing in the repo records `mobile`'s state after

1. **Is `mobile` still a fleet worker at all?** Unknown. Given a 6 GB card and no driver, the

2. **Was a worker ever re-installed on the Debian side?** Unknown — install dir, venv path, and

## 1. Overview

- **GPU arch:** Ampere, **sm_86** — important because it is **≥ sm_80**, the cutoff for the
  bf16 fused-MoE Triton kernel. The opt-in compiles and runs on this arch (validated on the
  RTX 3060, rel 0.006, ~3.9× on the routed-expert GEMM).
- **amdcomp (12 GB, Linux):** the workhorse 3060 — takes a real pipeline stage (many layers),
  is where the advanced MoE tier is enabled, and carries enough of the media stack to serve as
  a `can_t2i` / ACE-Step placement target (see [../T2A.md](../T2A.md), [../T2I.md](../T2I.md)).
- **mobile (6 GB, Debian):** see [§0](#0-mobile-status-after-the-debian-reinstall) — the card is
  offline for want of a driver. Were it running, 6 GB is too small for a whole model of any
  size: it contributes a **few layers in a distributed split**, or hosts a small model outright.
- Both serve int4 **dense** linears via torch **tinygemm** (`_weight_int4pack_mm`), the fast
  batch-1 path on NVIDIA — int4 beats bf16 on these cards.

## 2. Install

Both boxes want Python + a **CUDA 12.8 torch build** + the app deps. The 3060 is `cu128`-fine.

### amdcomp (Proxmox VE 9 / Debian 13)

The host driver is its own playbook — [../PROXMOX9_NVIDIA.md](../PROXMOX9_NVIDIA.md). Ampere is
Turing-or-newer, so it takes the **open** kernel modules (`nvidia-open-kernel-dkms`), and the
PVE-specific trap applies in full: pin kernel **6.14** and install `proxmox-headers-$(uname -r)`
rather than `linux-headers-*`. Do that first; the rest assumes `nvidia-smi` is green.

```bash
# Triton (for the fused-MoE opt-in) JIT-compiles launcher stubs, so it needs a C compiler
# and Python headers. Triton itself ships inside the Linux torch wheel — nothing to install.
apt install -y python3-venv python3-dev gcc git
python3 -m venv /root/imenv

# torch — CUDA 12.8 build (this box runs 2.11.0+cu128, the version T2A.md pins into the
# ACE-Step constraints file so the media install cannot move it):
/root/imenv/bin/pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128

# App deps (same versions as the rest of the CUDA fleet — from ROCM.md's dep list):
/root/imenv/bin/pip install \
    transformers==5.12.1 safetensors==0.8.0 huggingface_hub==1.19.0 \
    numpy==2.4.6 psutil==7.2.2 einops fastapi uvicorn

# Sanity check — must print True and run a matmul with no crash:
/root/imenv/bin/python -c "import torch; \
print('cuda', torch.version.cuda, '| avail', torch.cuda.is_available(), \
'|', torch.cuda.get_device_name(0)); \
a=torch.randn(2048,2048,device='cuda'); (a@a).sum().item(); print('matmul OK')"
```

> The `/root/imenv` path is the one [../T2A.md](../T2A.md)'s enablement recipe uses on this box
> (it names beast and amdcomp as the two CUDA hosts it was validated on). A fresh install
> elsewhere can put the venv anywhere; `~/imenv` is what the CPU and P620 guides use.
>
> (verify) PROXMOX9_NVIDIA.md §7 says match the wheel to the driver (550 → CUDA 12.4 → `cu124`),
> yet this box runs `cu128`. Same unreconciled discrepancy as on beast — see the note in
> [4070-ti-super.md §2](4070-ti-super.md#2-install).

### mobile (Debian 13) — *would-be* recipe, not a running node

⚠ Read [§0](#0-mobile-status-after-the-debian-reinstall) first: this is what bringing the card
back would take, and none of it has been done.

The **kernel-pin** step from PROXMOX9_NVIDIA.md §1 does **not** apply — that trap is specific to
Proxmox's own kernels, and this is plain Debian. What does carry over is the module-flavour rule
(Ampere → **open** modules, `nvidia-open-kernel-dkms` + `nvidia-driver` from `non-free`, headers
matching the running kernel, Secure Boot MOK enrollment if SB is on) and the verification order:
`nvidia-smi` green **first**, then torch.

```bash
# 1) driver (see PROXMOX9_NVIDIA.md §0/§2/§4/§5 for the generation table, repo lines, and MOK)
# 2) then, and only then, the venv:
python3 -m venv ~/imenv
~/imenv/bin/pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128
~/imenv/bin/pip install transformers==5.12.1 safetensors==0.8.0 huggingface_hub==1.19.0 \
    numpy==2.4.6 psutil==7.2.2 einops fastapi uvicorn
```

The fused-MoE opt-in is **not** worth enabling on a 6 GB card that holds a few layers — the
opt-in accelerates routed experts, and this node will rarely hold a MoE's expert layers.

## 3. Run the worker

### amdcomp — systemd **system** unit

The launch line (`--device gpu` for a pure-GPU stage, `cpu+gpu` to allow CPU spill — match the
unit):

```bash
/root/imenv/bin/python client.py --device cpu+gpu
```

**No `--controller` flag is needed.** `config.json` ships `controller_host: "auto"`, so the
worker finds the controller by UDP broadcast on `discovery_port` (50099) and retries every 30 s.
Pass `--controller <ip>` only for something broadcast cannot cross (subnet/VLAN/VPN), and be
aware an explicit flag **overrides `config.json`** — a stale one pins the worker to a dead
address. Don't edit `config.json` instead: it is in `EXTRA_UPDATE_FILES` and a self-update
reverts it.

Enable the **advanced MoE tier** via a systemd **drop-in**:

```ini
# /etc/systemd/system/im-worker.service.d/fused-moe.conf
[Service]
Environment=INFINITEMODEL_CUDA_FUSED_MOE=1
```

```bash
systemctl daemon-reload && systemctl restart im-worker
```

The fused forward installs at **load time**, so restart the worker *and reload the model* after
changing the env — a resident loaded under the old setting keeps it.

> **Unit names differ across the fleet, and it bites.** `amdcomp` and `beast` run
> **`im-worker.service`** (that is the name [../T2A.md](../T2A.md) tells you to restart after
> enabling ACE-Step on those two boxes); `work`, `steamdeck`, and the provisioning scripts
> (`provision_worker.sh`, `persist_worker.sh`) install **`infinitemodel-worker.service`**. Check
> `systemctl list-units 'im*worker*'` before assuming. (This resolves the older "verify the exact
> unit name" TODO that sat here; the **exact `ExecStart` line** — `--device`, `--name`, `--attn`,
> and whether a legacy `--controller` flag survives — is still not in this repo and remains
> unverified.)

### mobile

⚠ Nothing to document — see [§0](#0-mobile-status-after-the-debian-reinstall). If the box is
brought back with a working driver, it takes the same `client.py` launch as amdcomp
(`--device cpu+gpu`, discovery, one worker per box) under whatever unit the operator installs;

the guide — including that file's `MemoryMax` / `MemorySwapMax=0` cap, which matters more on a
laptop than on a rack box.

## 4. Optimal settings

**Quant:** **int4**. Dense int4 uses torch tinygemm on Ampere — already the fast batch-1 path,
and int4 beats bf16 (int4 7B 3.25 → 21.13 tok/s in [../ACCELERATION.md](../ACCELERATION.md)).
Use bf16 only if a small model fits comfortably and you want to skip dequant.

### amdcomp (12 GB)

- **Models that fit/run well:** a ~7B dense int4 fits whole; a small **MoE** (e.g. `olmoe:1b-7b`)
  is ideal — low active-param ratio → fast decode, and the fused-MoE opt-in gives the routed
  experts ~3.7× (validated: `olmoe:1b-7b` int4 **8.5 → ~31.5 tok/s** with `INFINITEMODEL_CUDA_FUSED_MOE=1`).
- **Placement:** as a real GPU stage in a pipeline split, or all-GPU for a model that fits in 12 GB.
- **Context:** moderate — KV competes with weights in 12 GB. Long prefill is chunked by default
  (`INFINITEMODEL_PREFILL_CHUNK=2048`); lower it for very long contexts on a tight box.
- **Prefer:** sparse MoE with low active params over a big dense model of the same footprint
  (decode tracks active bytes/token).
- **Media placement:** this box advertises `can_t2i` and serves ACE-Step, so a media load can
  land here and take VRAM the LLM planner was counting on. Pin deliberately
  (`POST /load?model=<m>&node=amdcomp`) rather than letting two schedulers fight.

### mobile (6 GB)

Offline — see [§0](#0-mobile-status-after-the-debian-reinstall). The tier guidance, should it
return: a **few layers in a distributed split**, or a small model (≤ a few B) at int4; never a
full mid/large model, because CPU spill on something that doesn't fit causes contention.

> On bandwidth-limited cards, prefer a sparse **MoE (~3B active)** over a dense model of similar
> quality — see "Choosing a fast model" in [../ACCELERATION.md](../ACCELERATION.md).

## 5. Verify

**Client self-test (load on GPU)** — confirms the worker can load weights onto the 3060:

```bash
/root/imenv/bin/python client.py --self-test-load --device gpu --quant int4
```

**Registration check** — the worker should appear in the controller's status with its GPU + VRAM:

```bash
curl -s http://<controller-ip>:21434/status
```

**Fused-MoE engaged (amdcomp)** — load a MoE and look for the self-check in the worker log:

```bash
curl -s "http://<controller-ip>:21434/logs?node=amdcomp"
# expect:  [int4] fused-MoE self-check ... -> ACTIVE
#  (-> fallback means it self-checked out / gcc+headers missing → safe bf16-remat path)
```

**Gen test** — a quick coherent-generation through the controller API confirms end-to-end
(load a model, then a short completion; "Paris" smoke test as used across the fleet).

## 6. Gotchas

- **`INFINITEMODEL_CUDA_FUSED_MOE=1` is Linux + Ampere-or-newer.** It engages on amdcomp
  (sm_86 ≥ sm_80). It is **opt-in**, not default. On a pre-Ampere card the bf16 kernel won't
  compile and the self-check falls back safely. The opt-in upgrades only the **routed-expert**
  GEMV; dense already uses tinygemm, which is why the end-to-end win is MoE-shaped. See
  [../ACCELERATION.md](../ACCELERATION.md).
- **Driver before torch, always.** `nvidia-smi` green but `torch.cuda.is_available()` False =
  a CPU-only wheel in the venv. The reverse — a CUDA wheel with no kernel module — is `mobile`'s
  current state and reports the same `False` for a completely different reason, so check
  `nvidia-smi` first and don't debug the venv for a missing driver.
- **A kernel upgrade can silently take amdcomp's GPU away.** Every PVE kernel change re-triggers
  a DKMS rebuild and the packaged 550 driver only builds on 6.14 — which is why 6.14 is pinned.
  Confirm `dkms status` before rebooting a remote host. ([../PROXMOX9_NVIDIA.md](../PROXMOX9_NVIDIA.md) §8.)
- **One worker per box.** Two workers sharing a hostname fight over the controller registration.
- **Perf-only kernel changes carry no VERSION bump** — a self-update *stages* the new code but
  does **not** auto-restart the worker. `systemctl restart im-worker` (or the controller's
  `POST /restart?workers=1`) to pick up a kernel change.
- **Env changes apply at load time.** After setting/clearing `INFINITEMODEL_CUDA_FUSED_MOE` (or
  any switch), restart the worker **and reload the model** — the fused forward installs during load.
- **Don't edit `config.json` to point the worker** — it's in `EXTRA_UPDATE_FILES` and a
  self-update would revert it. Use discovery, or `--controller` on the launch line.
- **Long-prompt prefill** is chunked by default (`INFINITEMODEL_PREFILL_CHUNK=2048`,
  standard-attention only). On a memory-tight box lower it (512–1024) for very long contexts;
  `0` disables. See [../ACCELERATION.md](../ACCELERATION.md).
